### Q2. 수동 CI vs 자동 CI — 무엇이 다른가요?
- 요구사항 #1에서 한 "로컬에서 직접 확인(수동 CI)"과
  요구사항 #3의 "GitHub Actions 자동 CI"의 차이는?
- 자동화로 무엇이 좋아졌나요? (사람의 실수, 반복 작업 관점)
---
| ✍️ 작성란 |
|-----------|
| **수동 CI(#1·#2):** TE가 테스트 스크립트를 로컬에서 직접 실행했다. #2 검증 때는 #1 스크립트도 다시 돌려 회귀를 확인했다. **자동 CI(#3):** `ci.yml`을 만든 뒤에는 PR을 열거나 `main`에 push할 때마다 문법 검사, 서버 기동, API curl, #1~#3 E2E(총 107건)가 약 1분 만에 자동으로 실행됐다. |
| **수동 CI의 한계를 직접 겪었다.** BE와 FE는 `main`에 push하기 전에 테스트를 돌리지 않았다. 그래서 BUG-1(대시보드 `/` 500 에러)은 TE가 실행하기 전까지 `main`에 그대로 있었다. 회귀 테스트도 "누군가 기억해서 돌려야" 실행된다. |
| **자동화로 좋아진 점:** ① 사람이 기억하지 않아도 push/PR마다 같은 검사가 빠짐없이 실행된다. ② 결과가 PR에 초록 체크로 남아 merge 판단 근거를 누구나 볼 수 있다. ③ 테스트 리포트가 Artifact(`te-reports`)로 남는다. ④ 스크립트가 FAIL 시 종료 코드 1을 반환하므로 그대로 merge 차단 조건이 된다. 요구사항 문서의 기본 CI(curl 3건)는 API만 확인한다. 그래서 BUG-1처럼 화면에서만 드러나는 결함을 잡도록 `GET /`과 Playwright E2E를 CI에 추가했다. |

### Q3. 수동 배포 vs 자동 CD(Render) — 어떤 차이를 느꼈나요?
- push만 했는데 자동 배포되는 경험은 어땠나요?
- 수동으로 서버에 올리는 것과 비교했을 때 장단점은?
---
| ✍️ 작성란 |
|-----------|
| CI 파이프라인에 "CI 통과 시에만 Render 배포" 단계(Deploy Hook)까지 넣어 두었다. 하지만 Render 서비스 연결과 Secret 등록을 마치지 못해 자동 배포가 실제로 일어나는 것은 확인하지 못했다. 대신 배포를 앞두고 다음 위험을 확인했다. |
| **장점(예상):** `main`에 merge만 하면 배포되므로 "어떤 버전이 서버에 올라가 있는지"가 `main`과 항상 일치한다. 수동 배포에서 생기는 파일 누락, 명령어 실수가 없어진다. |
| **단점/주의점:** 자동 배포는 깨진 코드도 자동으로 내보낸다. BUG-1은 `requirements.txt`에 버전 고정이 없어 최신 Starlette가 설치되면서 생겼다. Render도 배포할 때마다 최신 패키지를 설치하므로, 고치지 않았다면 배포 서비스에서도 500 에러가 났을 것이다. 그래서 **CD 앞에는 반드시 CI가 있어야 한다**고 판단했다. 방법은 Auto-Deploy 대신 CI 통과 시 Deploy Hook 호출, 그리고 의존성 버전 고정이다. 또 무료 인스턴스는 응답이 느려 BUG-2 같은 타이밍 문제가 로컬보다 잘 드러날 수 있다. 배포 후 `--base-url`로 E2E를 다시 돌리는 단계가 필요하다. |

### Q4. PR / 코드 리뷰 / 충돌 해결에서 배운 점은?
- 같은 파일(`app.js`)을 여러 명이 수정했을 때 충돌이 어떻게 발생했나요?
- 협업 과정에서 팀이 정한 규칙이 있었나요?
---
| ✍️ 작성란 |
|-----------|
| **충돌:** 실제 conflict는 발생하지 않았다. `app.js`는 FE(#2 구현, #3 badge)와 TE(BUG-2 수정)가 함께 수정했지만 수정 위치가 겹치지 않았다. 각각 `selectSubscriber()`와 `badgeClass()`였다. 충돌이 없었던 것은 운이 좋았던 것이지 규칙 덕분은 아니다. 대신 "충돌 없이 병합됐다"는 것이 "동작이 맞다"는 뜻은 아니라고 보고, merge 후 BUG-2 수정이 유지되는지 E2E로 다시 확인했다. |
| **PR / 리뷰:** 요구사항 #3에서 처음으로 PR(#1)을 사용했다. PR 본문에 작업 내용, 로컬 검증 결과, merge 조건(CI 통과)을 적고 CI 초록 체크를 확인한 뒤 merge했다. 다만 GitHub 리뷰 승인이나 코멘트는 남기지 않았다. 코드 리뷰는 주로 TE가 맡았고, 리뷰에서 결함 2건을 찾았다. BUG-2는 FE 코드를 읽다가 발견했고, 응답 지연을 재현해 확인했다. CSS-1(스켈레톤 CSS의 `.hidden` 무효화)은 개발 전에 FE에 공유해 구현 단계에서 고쳤다. 리뷰 결과가 PR 코멘트가 아니라 Report와 구두로만 전달된 점은 아쉽다. |
| **팀 규칙:** ① TE 검증 Report에서 PASS가 나온 뒤에만 `main`에 반영한다. ② 커밋 메시지는 `feat:` / `fix:` / `test:` / `docs:` / `merge:` 접두어를 쓴다(일부 커밋은 지키지 못함). ③ 요구사항 #3부터는 PR + CI 통과 후 merge하기로 했고, 실제로 PR #1에 적용했다(`req1_2_pm_te_summary.md` 5장). |

> **판단 근거:** 테스트 설계서를 개발 전에 작성했다. 자동 검증 107건(17+33+38+19)이 전부 PASS였고, 결함 3건을 `main` 반영 전에 모두 잡았다. 안정성은 높았다. 하지만 검증에 시간을 많이 써서 CI는 요구사항 #3에서야 붙었고, Render 배포까지는 실습 시간 안에 도달하지 못했다. 전달 속도가 병목이다.
> **먼저 할 일:** 이제 검증 스크립트가 CI에 연결됐으니 사람의 검증 시간이 줄어든다. 다음은 PR 단위의 작은 배치로 나누고, CI 통과 → Render 배포까지 자동으로 이어지게 만드는 것이다.

## 4. 팀 종합 소감

| ✍️ 작성란 |
|-----------|
| 요구사항 #1~#3 기능 구현과 TE 검증까지 마쳐 기능 품질에는 자신이 있다. 자동 검증 107건이 모두 PASS였고, 결함 3건(BUG-1, CSS-1, BUG-2)을 `main` 반영 전에 찾아 고쳤다. 세 건 모두 curl로 API만 확인해서는 드러나지 않았고 실제 브라우저로 화면을 검증해서 찾았다. "API가 된다"와 "사용자가 쓸 수 있다"는 다르다는 것을 배웠다. |
| 요구사항 #3에서는 feature 브랜치 → PR → CI 초록 체크 → merge 흐름을 처음으로 끝까지 경험했다. 그 전까지 손으로 돌리던 검증이 PR마다 1분 안에 자동으로 실행되는 것을 보며 자동화의 가치를 체감했다. 아쉬운 점도 있다. 초반에 `main` 직접 push를 허용해 PR과 리뷰 경험이 #3 한 번에 그쳤고, Render 배포(CD)는 마무리하지 못했다. |
| 다음 단계는 ① Render Web Service 연결과 `RENDER_DEPLOY_HOOK_URL` Secret 등록, ② 배포 URL에서 `--base-url`로 E2E 재실행, ③ 의존성 버전 고정과 `main` 브랜치 보호다. 새 프로젝트를 시작한다면 기능 개발보다 `main` 보호 + PR + CI를 먼저 세팅하겠다. |
